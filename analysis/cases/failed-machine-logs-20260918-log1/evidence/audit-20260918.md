## Findings

All 14 logs in this archive fail during process access or fallback reads with
Windows error 5 (access denied). The failure happens before a useful engine
operation result is available. The old package did not request administrator
execution, so an elevated target process could not be opened reliably. The
fullscreen error is a caller-level propagation of the same access failure.

Earlier external evidence also contained these independent failure classes:

- old bridge stage 1/2 installs with no callback, followed by retained
  allocations;
- a world operation that required `GroupEnumUnitsSelected` before dispatch;
- object registry selection reporting `Warcraft III module not found`;
- stale window rebinding;
- ambiguous multi-client selection represented as PID 0;
- logs that mixed trainer, game, and window PIDs.

## Current source audit status

- The PyInstaller spec does not force administrator execution. The game in
  the new reproduction runs at medium integrity, and forcing the trainer to
  high integrity caused the bridge's `SetWindowsHookExW` path to fail before
  callback delivery. The package now follows the caller's integrity level.
- The current route is `manual_map + WH_GETMESSAGE + PostMessage`, with
  callback verification and same-route cleanup/retry.
- World effects enumerate the current player rather than requiring
  `GroupEnumUnitsSelected`.
- Object discovery combines PSAPI and Toolhelp and selects the matching game
  image by fingerprint, with transient retry handling.
- Diagnostics keep `trainer_pid`, requested PID, game PID, target PID, target
  window PID, and window PID separate. An unknown target is no longer encoded
  as fake PID 0.
- Single-unit coordinate-field edits use the engine position batch and reject
  ambiguous multi-selection. Multi-unit teleport still uses the engine batch
  and accepts collision/formation readback from the engine.
- The user reported the current `eeh3` item path working; offline eeh3 fixtures
  pass. Live eeh3 was not independently triggered during this audit.

## Post-release reproduction correction

The later local failure log from PID `39968` showed a different issue from
the old external archive: the target game was medium integrity while the
`audit-r2` trainer was elevated. The failure occurred in the camera pre-step
of instant move, before any position batch, with `stage=2`,
`bridge_install_trace=0x105`, `exception=0xc0000005`, and no callback. The
same PID and camera entry point succeeded from the source process when both
ran at the caller's integrity. The fix is therefore to remove forced UAC from
the frozen package; it does not alter multi-unit movement or coordinate
calculation.

The follow-up implementation also checks trainer and target integrity levels
before any current-engine bridge install. Matching levels proceed; known
mismatches stop with an explicit restart message; unknown levels are left to
the existing process-access diagnostics rather than being guessed.

The restarted local game was tested as PID `18896`. The current-engine camera
entry succeeded, and a complete selected-group move returned 3 moved units at
`(-7628.375714273745, 4555.07646803438)`. The runtime report recorded medium
integrity on both trainer and game, `matched=true`, callback verification,
position/world completion, and safe resource release.

After the integrity guard and localization changes, the full suite completed
with `2326 passed, 17 skipped, 120 subtests passed`.
